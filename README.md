# Product Thinking · 产品需求分析三步法

面向互联网公司 PM（产品经理）和全栈工程师的中文 Agent Skill，帮助你在写 PRD、排需求优先级或进入开发之前，判断需求是否真实、功能是否值得做，以及怎样用更低成本验证。

工作流结合苏格拉底提问、第一性原理和奥卡姆剃刀：先把需求问清楚，再拆解用户价值与事实，最后比较方案，落到可执行的最小验证动作。

### 1. 苏格拉底提问：把需求拆成可判断的问题

**已澄清——题设事实，尚非一手用户证据：**

- 目标用户是每周汇总进度的项目负责人，目前通过复制任务信息制作周报。
- 目前只有业务方反馈，没有用户访谈、使用数据或付费证据。
- 可用资源是一名全栈工程师、一周时间。

**待验证——以下均为假设：**

| 关键假设 | 为什么会改变决策 |
|---|---|
| 复制任务是周报制作中的主要耗时环节 | 若主要耗时在分析进度，导出价值可能有限 |
| 现有任务字段足以支撑周报 | 若缺少历史变化或风险说明，CSV 仍需大量补录 |
| 负责人可以使用 CSV 完成后续整理 | 若格式转换增加负担，导出未必省时 |
| 多位负责人需要的字段和范围基本一致 | 若差异很大，统一报表容易膨胀 |
| 现有查询、权限和数据量支持一周内交付 | 若不成立，应缩小范围或继续人工验证 |

### 2. 第一性原理：用户需要的价值是什么

核心价值承诺是：**减少从任务数据到可提交周报之间的整理时间，同时保证内容准确。**

可以把流程拆成：

> 找到相关任务 → 复制数据 → 筛选和核对 → 解释变化与风险 → 组织周报

CSV 主要改善前两步；完整报表可能覆盖更多步骤，但需要额外理解周报口径、历史变化和展示要求。人工辅助可以先观察每一步的真实成本。

- **事实：** 题设中的周报场景每周发生。
- **假设：** 每周发生的工作，能转化为每周使用导出的需求。
- **习惯：** “报表应该有图表、模板、自动发送”属于常见方案偏好，不能作为开发依据。
- **推断：** 当前证据更适合验证数据获取是否有价值，尚不足以支持完整报表。
- **商业判断：** 潜在价值来自节省时间、减少遗漏；没有证据支持付费意愿、留存提升或收入增长。

### 3. 奥卡姆剃刀：比较三个方案

以下复杂度是相对判断，具体工期仍需检查现有实现。

| 方案 | 依赖假设 | 复杂度与成本 | 能验证什么 | 当前建议 |
|---|---|---|---|---|
| 完整报表：汇总、图表、模板等 | 用户口径相似，系统数据完整，自动生成结果可直接使用 | 高；一周交付风险最大，维护面广 | 自动报表整体价值，但失败原因难定位 | 暂缓 |
| 简单 CSV 导出 | 获取数据是瓶颈，固定字段足够，用户能继续加工 | 低至中；取决于权限、查询和数据量 | 自助获取数据是否节省时间 | 验证通过后的首版 |
| 人工辅助：按固定字段整理 CSV 并交付 | 能接触真实负责人，用户愿意用实际周报任务试用 | 开发成本最低；人工成本随用户数增长 | 字段是否够用、数据是否可用、是否减少整理工作 | 开发前优先采用 |

人工服务若包含额外分析、润色或补录，可能让用户认可“人工代写周报”，无法证明 CSV 的价值。因此验证时应限制交付内容，并单独记录额外帮助。

### 4. 开发前最小验证动作

**核心假设：** 固定字段的任务 CSV 可以减少制作真实周报的总时间，且不会增加核对或补录负担。

**目标用户与样本建议：** 找 3 名正在负责周报、目前需要复制任务的项目负责人。小样本用于发现问题和决定是否投入首版，不能推算整体需求比例。

**动作与时间建议：** 开发前投入半天至一天，由 PM 主导。

1. 每人安排约 30 分钟，结合最近一份周报，观察其如何选任务、复制、核对和整理。记录各环节耗时，区分现场观察和用户回忆。
2. 用允许访问的任务数据，人工生成同一套固定字段 CSV；让负责人用于当前真实周报，记录剩余工作及额外帮助。
3. 对比端到端整理时间、遗漏或错误、缺失字段，并询问下周是否愿意继续使用。

**成功标准——仅为待确认的建议，需在试验前约定：**

- 3 人中至少 2 人能使用固定 CSV 完成实际周报，不依赖额外代写。
- 相比各自原流程，端到端整理时间减少至少 30%，且没有增加遗漏或错误。
- 至少 2 人愿意在下一次周报继续使用；下一周实际复用作为后续证据。

这些数字是建议决策门槛，**不是已有数据，也不是统计显著性结论**。若基线仅来自回忆，时间改善只能作为初步信号。

**失败后的处理：**

- 主要耗时在解释、协调或写结论：暂缓导出开发，重新定位瓶颈。
- 字段缺失但需求一致：调整人工样例后再试。
- 各人要求差异很大：先限定一种负责人或一种周报场景。
- 数据正确性或权限无法保证：先解决交付前提，不进入开发。

### 5. 验证通过后的首版范围

**首版建议：单个项目内，导出当前筛选结果的任务 CSV。** 这依赖现有任务列表、筛选能力和权限机制可复用；否则需要重新评估一周范围。

| 纳入首版 | 边界 |
|---|---|
| 一个导出入口 | 放在现有任务列表，明确导出当前筛选范围 |
| 固定字段 | 候选为任务 ID、标题、状态、负责人、截止日期、更新时间、任务链接；以验证结果定稿 |
| 当前任务快照 | 不声称提供“本周变化”；历史变化需要历史数据支持 |
| 权限与正确性 | 仅导出用户有权查看的任务和字段；不静默截断或漏行 |
| 基础可用性 | 中文和常见表格软件可正常打开；处理分隔符、换行及公式注入 |
| 最少量观察 | 记录导出成功、失败，并向试用负责人收集真实使用反馈 |

首版暂不包含跨项目汇总、自定义模板、图表、定时发送、PDF/Excel 多格式、自动生成总结和历史趋势。

建议将一周分为：前一天验证并检查技术前提，随后完成最小导出，最后留出数据与权限校验、真实周报试用和修复时间。**验证不通过就停止开发，技术前提不成立就缩小范围，不以压缩正确性检查换取上线。**

### 6. 风险和下一步

主要风险是把“业务方提出功能”误当成“用户已有强需求”，以及把“CSV 导出成功”误当成“周报制作更高效”。人工辅助也可能高估效果，应把人工整理时间计入成本。

下一步按顺序执行：

1. PM 约真实负责人，用实际周报完成最小验证。
2. 工程师检查查询复用、权限、数据量和字段可用性，再确认首版能否一周交付。
3. 达到预先约定的门槛后开发 CSV；下一周观察实际复用，再决定是否扩展报表能力。

## 适用人群

- **PM / 产品经理**：梳理业务方或用户提出的需求，明确目标用户、使用场景、问题证据、需求边界与成功标准，为 PRD 和需求评审提供依据。
- **全栈工程师 / 研发人员**：承接模糊需求或独立负责产品时，先厘清“为什么做、解决什么问题、先做哪一部分”，再决定实现范围，减少无效开发。

## 适用场景

- **需求分析**：面对“用户说想要”“业务方要求加一个功能”，判断背后的问题是否真实，以及现有方案为什么不够用。
- **需求评审与优先级**：比较做、不做或轻量替代方案，明确核心需求与边缘需求，收敛首版范围。
- **产品迭代**：分析转化、留存或流失问题，区分事实与假设，避免直接把问题归因于功能不足。
- **商业化判断**：分析定价、订阅与商业模式是否符合用户价值及使用频率。
- **开发前验证**：把产品想法拆成用户访谈、人工交付或低保真原型等最小实验，明确验证动作和成功标准。

典型输出包括问题重述、关键判断、事实与假设、方案比较、最小验证方案和下一步，可作为需求讨论与 PRD 编写的输入。判断质量依赖你提供的背景和证据，仍需结合真实用户反馈与团队评审。

### 下载与安装（整段复制到终端）

这段命令会从公开 GitHub 仓库克隆当前版本，只复制技能需要的文件和许可证，并在退出时删除下载临时目录；不会上传本地项目。已存在同名安装时会停止，请先检查已有版本。

```bash
(
  set -eu
  command -v git >/dev/null

  cp -R "$download_dir/product-thinking/rules" "$skill_dir/"
```

### 常见问题

- `codex: command not found`：先安装 Codex CLI，或修复终端 `PATH`。
- 登录失败、模型无权限、额度不足或网络错误：先解决 Codex 账号和连接问题；安装技能本身不会提供模型访问权限。
- 找不到技能：检查 `~/.agents/skills/product-thinking/SKILL.md` 存在，并重启 Codex；检查配置中是否禁用了该技能。
- 提示同名技能已存在：检查 `~/.agents/skills/` 和 `${CODEX_HOME:-~/.codex}/skills/` 的已有目录或软链接，再决定保留哪个版本；不要直接覆盖未知文件。
- GitHub 克隆失败：检查 GitHub 的 HTTPS 连接；安装命令会清理下载临时目录。若复制阶段中断，先检查目标目录是否完整，再决定是否重新安装。
