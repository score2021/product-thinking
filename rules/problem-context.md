# 问题上下文加载

目标：在开始分析前，先识别已有上下文和关键缺口，避免重复问用户已经给过的信息。

## 1. 先读取已有材料

如果用户提供或引用了以下材料，先读取相关内容：
- 产品想法、PRD、需求描述、逐字稿、会议纪要
- 数据指标、用户反馈、客服记录、访谈记录
- 竞品说明、截图、流程图、定价页
- 已有 Prompt、Skill、工作流文档

只读取当前问题相关部分，不一次性加载无关大文档。

## 2. 建立上下文清单

在内部梳理以下维度：

| 维度 | 要判断什么 |
|------|------------|
| 目标用户 | 谁遇到这个问题 |
| 使用场景 | 问题在什么时刻发生 |
| 当前替代方案 | 用户现在不用这个产品时怎么解决 |
| 痛点成本 | 时间、钱、风险、认知、协作成本 |
| 价值形态 | 持续价值还是一次性价值 |
| 行为频率 | 高频、周期性、低频、一次性 |
| 付费动机 | 离不开、省成本、降风险、强需求 |
| 成功标准 | 什么指标说明判断成立 |
| 约束条件 | 时间、人力、技术、渠道、合规、品牌 |

## 3. 一次只问一个问题

如果缺少会改变结论的关键上下文，只问一个最重要的问题。

优先级：
1. 目标用户是谁
2. 用户现在怎么解决
3. 痛点或成本是否真实
4. 成功标准是什么

## 4. 可继续时先分析

如果信息不完整但足以推进，先标注假设继续分析，例如：

```markdown
以下基于两个假设：
- 假设目标用户是中小团队产品负责人
- 假设当前目标是判断功能优先级，而不是写完整 PRD
```

## 禁止行为

- 不读用户已给材料就追问
- 一次问多个问题
- 因信息不完整而停止分析
- 把猜测写成事实
